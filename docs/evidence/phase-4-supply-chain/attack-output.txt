Phase 4 — supply-chain image-signing attack demo (captured 2026-07-25)
Cluster: kind seclab (context kind-seclab), Kubernetes v1.35.5.
Admission controller: Kyverno v1.18.2 (reg.kyverno.io/kyverno/kyverno:v1.18.2).
Policy: ImageValidatingPolicy require-keyless-signed-ghcr
(policies/supply-chain/require-signed-images.yaml), validationActions [Deny],
failurePolicy Fail, matching images under the glob
ghcr.io/joesevv/k8s-security-lab/* in namespaces demo + demo-kyverno-only, on
pods, pods/ephemeralcontainers, apps/v1 workloads and batch/v1 jobs.

Threat blocked: "an attacker runs an image this project never built." Registry
allow-listing (phase 2b) only proves WHERE an image came from, not WHO built
it — anyone with push access to the org, or a compromised CI step, can put a
tampered image at a trusted path. A cosign keyless signature binds the image
DIGEST to the OIDC identity of one specific GitHub Actions workflow on one
specific ref, recorded in the Rekor transparency log. Kyverno verifies that
signature at admission, so an image that did not pass through the trusted
producer never runs.

SCOPE OF THE CLAIM: a signature attests PROVENANCE, not safety. It proves who
built the bytes and that they have not changed since. It says nothing about
CVEs — Trivy runs report-only in CI (exit-code 0), so a vulnerable image is
still signed and still admitted. See runbooks/phase-4-supply-chain.md.

The trusted artifact under test:

============================================================
1) POSITIVE CONTROL — the SIGNED image is admitted. Server-side dry-run is used
deliberately: a plain `kubectl apply` on an unchanged object is a no-op that can
report "unchanged" without the mutating/validating webhooks ever weighing in.
`--dry-run=server` forces the request through the full admission chain,
including the signature webhook, and changes nothing.
$ kubectl apply -f workloads/signed-app/deployment.yaml --dry-run=server
============================================================
deployment.apps/signed-app unchanged (server dry run)
(exit code: 0)

Methodology proof — `--dry-run=server` really does invoke the signature webhook,
so the exit 0 above is a genuine admission pass and not a skipped check. The
SAME flag on the unsigned attack manifest is denied by that same webhook:

============================================================
2) HEADLINE — an image that REALLY EXISTS and really has NO signature is DENIED,
by the POLICY's own verdict. The reference is cosign's own signature artifact
for the signed app, published by the same workflow under the OCI 1.1
referrers-fallback tag sha256-<digest-of-the-signed-image>. It is a genuine,
pullable manifest sitting under the enforced glob — and, being a signature
itself, nothing ever signed IT. That makes it the strongest available negative:
the registry resolves it fine, so the denial can only come from signature
verification.

violation: the image resolved and its signature did not verify.

============================================================
4) CONTROLLER PATH — the same unsigned artifact is denied in a DEPLOYMENT, not
just a bare Pod. Enforcement on apps/v1 rests on hand-written resourceRules, not
on Kyverno autogen (the live policy has no spec.autogen and status.autogen is
{}), so it is proven separately rather than assumed. The manifest is the REAL
signed-app Deployment with only the image (and its name/labels) rewritten —
every other field is byte-identical to the workload that passes in case 1, so
the image reference is the sole variable.

NOT PROVEN HERE — stated so the evidence above is not read as more than it is.
============================================================
- cosign is NOT installed on this host, so no local `cosign verify` transcript
  is part of this capture. The ONLY verification demonstrated here is in-cluster,
  at admission (cases 1, 2, 4). The workflow's own `cosign verify` self-check is
  written but has never executed — see the next bullet — so it proves nothing
  yet.
- The two-job (build-scan || sign) shape of .github/workflows/supply-chain.yml
  has NOT yet run. The signed artifact under test was produced by the earlier
  single-job version of the workflow. The split, the SHA-pinned actions and the
  cosign verify self-check are unproven until the next run, and
  docs/evidence/phase-4-supply-chain/cosign-verify.txt does not exist yet.
- Trivy runs report-only (exit-code: '0'). No CVE finding has ever blocked a
  signature. Provenance != absence of vulnerabilities.
- The SBOM is uploaded as a CI artifact only. It is not a cosign attestation
  bound to the image digest, so no admission policy can verify it. Known gap.
