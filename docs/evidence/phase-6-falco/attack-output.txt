FALCO DETECTS. IT DOES NOT PREVENT. THIS IS THE FIRST SENTENCE ON PURPOSE.
Every phase before this one ships something that REFUSES an attack and then
proves the refusal: RBAC denies, Kyverno denies, PSA denies, NetworkPolicy
drops, sealed-secrets makes the plaintext absent, the ImageValidatingPolicy
refuses an unsigned image. Falco does none of that. When a rule matches it
writes ONE LINE to its own container's stdout and the attack continues. Both
attacks in section 2 below succeeded. Section 3 is the proof that they
succeeded, and section 3 is the honest heart of this file — not section 2.

FILENAME, SINCE IT DOES NOT DESCRIBE THE CONTENTS: this file is named
attack-output.txt to match the other six phases and because five manifests in
this directory already point at that name. It is a DETECTION transcript, not a
denial transcript. Section 4 is the only part of it where anything is refused,
and the thing refused there is the sensor itself.

AN ALERT IS NOT A CONTROL. There is no alerting pipeline in this lab. The
alert's entire lifetime is: written to the falco container's stdout -> the
kubelet's container log on that node -> gone at pod restart or log rotation.
falcosidekick is deliberately not installed, file_output is off, http_output is
off with an empty url, program_output is off, json_output is off, and
responseActions is off. Nothing routes an alert, nothing stores it, nothing
pages anybody, and nothing acts on it. All of that is shown, command by
command, in section 3 — it is evidence, not a disclaimer.

SCOPE OF THE DETECTION, STATED BEFORE THE ALERTS: TWO distinct behaviours were
fired at the pinned install, against TWO stock rules. In the 2026-07-29 ATTACK
WINDOW that produced THREE alert lines, not two: the terminal-shell behaviour
was rehearsed once, 50 seconds before the marked attack and without a marker
string, and it fired the same rule; that third line is in the log and is
printed and accounted for in 2f rather than dropped.
DO NOT READ A TOTAL LINE COUNT AS A RESULT. THE LOG ONLY GROWS. Nothing
deduplicates a Falco alert and nothing removes one until the pod restarts, so
the number of lines `kubectl logs` returns is a function of WHEN YOU LOOK, not
of what this phase demonstrated. It is already larger than three: a later
adversarial verification pass re-fired both behaviours against the live
cluster and added two more lines, which 2f prints and attributes. Section 0
destroys an entire earlier install so that no alert can be silently inherited,
and the same standard is applied here: every alert in this pod's log is
listed and attributed, whether or not it belongs to this phase. THE EVIDENCE
IS THE TWO DEMONSTRATED BEHAVIOURS AND THE TWO STOCK RULES THEY FIRED — both
of which are fixed, and neither of which changes when the log gets longer.
Nothing here measures what would have slipped past, and section
2e records one behaviour — the textbook `cat /etc/shadow` — that this lab's own
hardening makes INVISIBLE to the stock rule.

THIS IS NOT A THREE-NODE DETECTION FLEET. The three kind nodes share one
kernel and the modern eBPF probe is attached to that one kernel, so all three
Falco pods see every event on the whole cluster. Each alert below appears
THREE times, at near-identical nanosecond timestamps, and only the pod
co-located with the target's containerd can resolve the container and k8s
fields — the other two print <NA>. Section 2c shows this. Any count of
"detections" taken from these logs must be divided by three or the lab claims
3x the reality. This is a kind-on-Docker-Desktop artifact and does NOT
describe Falco on a real multi-node cluster.

RULE NAMES ARE A NAMED UNVERIFIED INPUT. Falco runs here with
json_output: false, so each alert line carries a PRIORITY and the rule's
OUTPUT STRING, and never the rule's name. The working notes behind this phase
name the two rules "Terminal shell in container" and "Execution from
/dev/shm". NO COMMAND WAS RUN to read those names out of the loaded
/etc/falco/falco_rules.yaml, so they appear below only as an identification
against the stock ruleset, never as a captured field. What IS captured, and
what every claim here rests on, is the priority and the message text, both of
which appear literally in the alert lines.

- THE COVERAGE CLAIM IS TWO RULES, AND IT IS NOT A LINE COUNT. Two behaviours
