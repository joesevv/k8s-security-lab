============================================================
0) WHAT 6b CHANGES, AND WHAT IT STILL DOES NOT. THE HONESTY THESIS, UP FRONT.
============================================================

PHASE 6 SAID: "Falco writes a line to a file descriptor and the line's next
hop does not exist." THAT SENTENCE IS NOW FALSE, AND ONLY THAT SENTENCE. The
next hop exists: Falco POSTs JSON to a Service, falcosidekick accepts it, and
falcosidekick writes it into a Redis that a Web UI reads. That is the whole
of what this phase adds.

FALCO STILL DETECTS AND STILL DOES NOT PREVENT. Nothing in 6b blocks, kills,
evicts, quarantines or denies anything. The attack in section 5 SUCCEEDED —
it printed its output and its shell ran to completion — exactly as both
attacks in phase 6 did. 6b earns no row in the threat model's Control →
ATT&CK table for the same reason phase 6 earned none: routing an alert is not
a mitigation.

STILL NOBODY IS PAGED. There is NO on-call, NO rota, NO owner, NO
notification and NO external sink of any kind. falcosidekick supports fifty
destinations; exactly one is enabled here and it is the in-cluster Web UI —
proven from falcosidekick's own startup line in section 7, not from the
chart's intent. An alert that reaches a dashboard nobody opens is still an
alert nobody reads. The difference 6b makes is narrower and worth stating
exactly: the alert now OUTLIVES the sensor that raised it, and can be
retrieved after the fact by a human who goes looking. That is the whole
delta, it is demonstrated in section 6, and it is not the same thing as
having a response capability.

AND THE RETENTION IS WORSE THAN THE PVC SUGGESTS. Section 7 TESTS the store
rather than reading its spec, and the tested answer is bad: the Redis has a
real 1Gi PersistentVolumeClaim, Bound, and it still lost every event when its
pod was deleted, because redis-stack's default RDB save thresholds were never
reached and no snapshot had ever been written. Worse, the ingest path did not
merely lose the data — it STAYED BROKEN until the Web UI pods were manually
restarted. Both are recorded with the commands that found them.

THE SENSOR'S OWN LOGS ARE STILL THE SAME DISPOSABLE THING THEY ALWAYS WERE.
Section 1 captures four real alert lines that existed before this upgrade, and
section 1c shows them gone — destroyed by the very DaemonSet restart that
installed the fix. That is not bookkeeping. It is the problem 6b addresses,
demonstrated once more on the way past.

THE PHASE ADDS ATTACK SURFACE AND SECTION 8 STATES IT. Three new images, five
new pods, a Redis with no password, and a Web UI whose Secret carries the
chart's default credential `admin:admin`. All of it runs in a namespace with
PSA `enforce: privileged` and outside every Kyverno policy's namespaceSelector.
Section 8 reads the apiserver's own verdict on whether these pods would pass
`restricted` if anything gated them. They would not — but they fail on four
categories, not phase 6's six, and the difference is stated because "could be
gated and is not" is a more useful sentence than "is not gated".

============================================================
8) THE ATTACK SURFACE THIS PHASE ADDS
============================================================

8a. FIVE NEW PODS, THREE NEW IMAGES, NONE OF THEM GATED BY ANYTHING. The
`falco` namespace is `pod-security.kubernetes.io/enforce=privileged`, and
Kyverno's four ValidatingPolicies and its ImageValidatingPolicy are scoped by
namespaceSelector to [demo, demo-kyverno-only]. Nothing on this cluster
evaluated any of these workloads. Phase 6 section 1f already conceded that for
the sensor; 6b puts four more pods behind the same exemption, and two of them
are network services rather than a read-only agent.

8b. WOULD THEY PASS `restricted` IF ANYTHING GATED THEM? NO — BUT READ HOW
THEY FAIL, BECAUSE IT IS NOT HOW FALCO FAILS. The namespace's `warn:
restricted` label made the apiserver answer this for free during the section 3
upgrade. Three of its four warnings are about the new workloads:

  falcosidekick-ui + wait-redis :  allowPrivilegeEscalation, capabilities,
                                   runAsNonRoot, seccompProfile   (4)
  falcosidekick                 :  allowPrivilegeEscalation, capabilities,
                                   runAsNonRoot, seccompProfile   (4)
  redis                         :  allowPrivilegeEscalation, capabilities,
                                   runAsNonRoot, seccompProfile   (4)
  falco + falcoctl (unchanged)  :  privileged, allowPrivilegeEscalation,
                                   capabilities, restricted volume types
                                   (12 hostPath mounts), runAsNonRoot,
                                   seccompProfile                 (6)

(The table above is a COUNT of the categories named in the four verbatim
warnings quoted in section 3; it is a summary of that output, not a separate
capture.)

=> FOUR CATEGORIES, NOT SIX. None of the three new workloads is `privileged`,
   none uses a `hostPath`, none requests a host namespace. What they are
   missing is four fields that are pure boilerplate to add:
   `allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]`,
   `runAsNonRoot: true`, `seccompProfile.type: RuntimeDefault`. The
   falcosidekick and UI Deployments already set `runAsUser: 1234` and
   `fsGroup: 1234` at pod level (read from the rendered spec), so they are
   ALREADY running as non-root — they just never assert it in the field PSA
   reads. The redis StatefulSet sets no securityContext at all.
   SO THE HONEST SENTENCE IS "COULD BE GATED AND IS NOT", not "cannot be
   gated". The chart exposes `securityContext` values for every one of these
   containers. Closing this is a values change, not a redesign, and it was NOT
   done in this phase — deliberately, because the spec for 6b was routing, and
   changing the hardening posture in the same upgrade would have made it
   impossible to say which change caused what.

8c. A REDIS WITH NO PASSWORD, REACHABLE BY ANY POD ON THE CLUSTER. Section 5d
and 7a retrieved and destroyed every stored alert with plain `redis-cli` and
no credential. The subchart's `webui.redis.password` default is the empty
string and it was left there; no NetworkPolicy in this repo covers the `falco`
namespace. THE ALERT STORE IS THEREFORE READABLE AND WRITABLE, WITHOUT
AUTHENTICATION, BY ANYTHING THAT CAN REACH 10.96.245.44:6379. An attacker who
lands anywhere on this cluster can delete the record of their own detection —
which section 7a demonstrates is a one-command operation, even if it did it by
accident.
