============================================================
0) WHAT 6b CHANGES, AND WHAT IT STILL DOES NOT. THE HONESTY THESIS, UP FRONT.
============================================================

PHASE 6 SAID: "Falco writes a line to a file descriptor and the line's next
hop does not exist." THAT SENTENCE IS NOW FALSE, AND ONLY THAT SENTENCE. The
next hop exists: Falco POSTs JSON to a Service, falcosidekick accepts it, and
falcosidekick writes it into a Redis that a Web UI reads. That is the whole
of what this phase adds.

FALCO STILL DETECTS AND STILL DOES NOT PREVENT. Nothing in 6b blocks, kills,
evicts, quarantines or denies anything. The attack in section 5 SUCCEEDED —
it printed its output and its shell ran to completion — exactly as both
attacks in phase 6 did. 6b earns no row in the threat model's Control →
ATT&CK table for the same reason phase 6 earned none: routing an alert is not
a mitigation.

STILL NOBODY IS PAGED. There is NO on-call, NO rota, NO owner, NO
notification and NO external sink of any kind. falcosidekick supports fifty
destinations; exactly one is enabled here and it is the in-cluster Web UI —
proven from falcosidekick's own startup line in section 7, not from the
chart's intent. An alert that reaches a dashboard nobody opens is still an
alert nobody reads. The difference 6b makes is narrower and worth stating
exactly: the alert now OUTLIVES the sensor that raised it, and can be
retrieved after the fact by a human who goes looking. That is the whole
delta, it is demonstrated in section 6, and it is not the same thing as
having a response capability.

AND THE RETENTION IS WORSE THAN THE PVC SUGGESTS. Section 7 TESTS the store
rather than reading its spec, and the tested answer is bad: the Redis has a
real 1Gi PersistentVolumeClaim, Bound, and it still lost every event when its
pod was deleted, because redis-stack's default RDB save thresholds were never
reached and no snapshot had ever been written. Worse, the ingest path did not
merely lose the data — it STAYED BROKEN until the Web UI pods were manually
restarted. Both are recorded with the commands that found them.

THE SENSOR'S OWN LOGS ARE STILL THE SAME DISPOSABLE THING THEY ALWAYS WERE.
Section 1 captures four real alert lines that existed before this upgrade, and
section 1c shows them gone — destroyed by the very DaemonSet restart that
installed the fix. That is not bookkeeping. It is the problem 6b addresses,
demonstrated once more on the way past.

THE PHASE ADDS ATTACK SURFACE AND SECTION 8 STATES IT. Three new images, five
new pods, a Redis with no password, and a Web UI whose Secret carries the
chart's default credential `admin:admin`. All of it runs in a namespace with
PSA `enforce: privileged` and outside every Kyverno policy's namespaceSelector.
Section 8 reads the apiserver's own verdict on whether these pods would pass
`restricted` if anything gated them. They would not — but they fail on four
categories, not phase 6's six, and the difference is stated because "could be
gated and is not" is a more useful sentence than "is not gated".

F5 — WHAT THIS PROVES.

C1 READ THE `save` SEMANTICS CORRECTLY. `save 3600 1` came due, a snapshot was
written without anyone asking for one, and the store then survived a restart

snapshot of its own and still came up with seven keys and an index it could
only have read off disk.

SIX MINUTES OLD, not a demonstration that a snapshot is never written. 7a's
own closing sentence — "The events were lost because no snapshot had been

and the threat model, that at this event volume an RDB snapshot trails the
writes it protects BY UP TO AN HOUR, now has a measurement behind it rather
than only redis's documented semantics: 3802 s, once, on this lab.

F6 — WHAT THIS DOES NOT PROVE, WHICH IS THE LONGER LIST.

- IT DOES NOT MAKE THE STORE DURABLE IN ANY STRONG SENSE. `appendonly` is
