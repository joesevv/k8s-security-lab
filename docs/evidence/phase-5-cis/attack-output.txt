Phase 5 — kube-bench CIS Benchmark assessment (report captured 2026-07-26;
triage probes 2026-07-28; re-verified 2026-07-29)
Cluster: kind seclab (context kind-seclab), Kubernetes v1.35.5, 3 nodes
(seclab-control-plane, seclab-worker, seclab-worker2).
Scanner: kube-bench v0.15.6, image docker.io/aquasec/kube-bench:v0.15.6
@sha256:861900910eec45b54a97e4a2af81b16fae7203d768f7f8e7de3b7456807870f5,
run as two run-once Jobs in namespace cis-benchmark. The benchmark is PINNED
with --benchmark cis-1.12; that pin is proved, not asserted, in section 2.

FILENAME, SINCE IT DOES NOT DESCRIBE THE CONTENTS: this file is named
attack-output.txt to match the other five phases and because three manifests
in this directory already point at that name. It is NOT an attack transcript.
Section 1 is the only adversarial-shaped capture in it, and the "attacker"
there is a benign scanner being refused. Everything after section 1 is an
assessment.

NOTHING IN THIS PHASE ENFORCES ANYTHING. Every other phase in this repo ships
a control that BLOCKS something and then proves the block. This one ships a
scanner that MEASURES. No policy was added, no namespace label on demo was
changed, no apiserver flag was altered, and not one CIS finding below was
remediated. The only thing section 1 demonstrates being blocked is the scanner
itself, by controls that already existed before this phase. A reader who takes
"kube-bench ran" as "the cluster was hardened" has read this exactly
backwards.

THIS IS A TEACHING ARTIFACT, NOT A COMPLIANCE RESULT. kind is not a production
cluster. Its three "nodes" are containers sharing one WSL2 kernel, its
control-plane components are kubeadm static pods, and the large majority of
the PASSes below are kubeadm's defaults rather than decisions this lab made. A
passing or failing score here does not transfer to any other cluster, and it
is not an audit result. Read the counts as "what this scanner said about this
particular kind cluster on this particular day" — never as "N% CIS compliant".
TWO OF THE SCANNER'S OWN RESULTS ARE DEFECTIVE, IN OPPOSITE DIRECTIONS: section
6 records a PASS that is outright wrong, and 5a / 5d-a record a WARN kube-bench
emitted without ever reading the file the check is about, which hid a real
1.1.9 finding until a direct stat exposed it.

SCOPE OF THE SCAN, STATED BEFORE THE NUMBERS: a Job produces ONE Pod, so the
node target ran on seclab-worker only. seclab-worker2 was NEVER scanned by
kube-bench. Its two node findings were confirmed by hand (probe 5d-d), as was
the 1.1.9 CNI file mode on all three nodes (probe 5d-a), but those are manual
checks, not kube-bench results. Scanning every worker needs a DaemonSet, which
this phase does not ship.

BENCHMARK VERSION, WITH ITS CAVEAT: cis-1.12 is the newest generic CIS config
kube-bench v0.15.6 ships, but that config's own version_mapping stops at
Kubernetes "1.34" and this cluster is v1.35.5. cis-1.12 is therefore applied
ONE MINOR VERSION AHEAD of the newest Kubernetes release its authors mapped it
to. It is the closest available match, not a declared match. CIS Benchmark
releases lag Kubernetes releases; that is normal, and it is stated here so
nobody writes "cis-1.12 is the CIS benchmark for Kubernetes 1.35". It is not.

1) THE SCANNER IS REFUSED BY THE CLUSTER'S OWN HARDENING — and the control
that refuses it is NOT the same one at both levels. Read which one answers
rather than assuming. kube-bench needs hostPID and hostPath mounts of node
paths; that is a restricted-profile violation, so PSA enforce=restricted on
demo rejects it, and that rejection is CORRECT BEHAVIOUR, not a bug. Applied
with --server-side --dry-run=server, which is a real admission request that
persists nothing. A plain --dry-run=server against an unchanged object
computes an empty patch and never reaches the server at all, so it would prove
nothing.

=> READ THE VERDICT, DO NOT ASSUME IT. Two things changed at the Job level.
First, PodSecurity only WARNED — 'restricted:latest', which is the warn label,
not the enforce one — and would have ADMITTED. PSA enforcement is evaluated
against PODS; against a batch/v1 Job it warns and admits. With PSA alone the
Job object would exist and then never produce a Pod, the rejection surfacing
only in Job controller events: a silent failure instead of a loud one. Second,
the actual denial came from KYVERNO, and NOT for hostPID or hostPath. It fired
restrict-registries, because docker.io/aquasec/* is outside the allow-list.
Writing "Kyverno blocks kube-bench because it is privileged" would exceed
enforced reality: no ValidatingPolicy in policies/ covers hostPID or hostPath
at all. Note also that require-drop-all-capabilities did NOT fire on this
spec, because the master Job drops ALL capabilities.

THE BENCHMARK PIN — "Assuming default version 1.18" IS COSMETIC, AND THAT IS
PROVED TWO INDEPENDENT WAYS RATHER THAN ASSERTED. A reader who sees that
warning in sections 3 and 4 will reasonably conclude a v1.35 cluster was
graded against the benchmark for v1.18. It was not.
$ kubectl -n cis-benchmark get job kube-bench-master -o jsonpath='{.spec.template.spec.containers[0].command}'
$ kubectl -n cis-benchmark get job kube-bench-node   -o jsonpath='{.spec.template.spec.containers[0].command}'
["kube-bench","run","--v=1","--benchmark","cis-1.12","--targets","master,controlplane,etcd,policies","--include-test-output"]
["kube-bench","run","--v=1","--benchmark","cis-1.12","--targets","node","--include-test-output"]
(exit code: 0)

PROOF 1 — the log lines must be read TOGETHER, not the warning alone. --v=1 is
set on both Jobs precisely so the report is self-proving here. FOUR lines are
common to both Jobs, in this order:
  Warning: Kubernetes version was not auto-detected ... Assuming default version 1.18
  util.go:395] Unable to get Kubernetes version from kubectl, using default version: 1.18
  common.go:351] Kubernetes version: "" to Benchmark version: "cis-1.12"
  common.go:274] Using config file: cfg/cis-1.12/config.yaml
The FIFTH line is PER-JOB, not shared, because each Job loads the test file for
its own target:
  master Job: common.go:78] Using test file: cfg/cis-1.12/master.yaml
  node Job:   common.go:78] Using test file: cfg/cis-1.12/node.yaml
Both are under cfg/cis-1.12/, which is all the pin argument needs; the master
Job goes on to load controlplane.yaml, etcd.yaml and policies.yaml from that
same directory. Each line above appears at the top of section 3 (master) or
section 4 (node) in full, with its glog timestamp and PID prefix; the only
editing here is the '...' elision in the Warning line, which is bare stderr and
carries no glog prefix.
The kube version is the EMPTY STRING "" at the point the benchmark is
resolved. The detected 1.18 was never consulted: in cmd/common.go,
getBenchmarkVersion only looks at the detected version inside `if
isEmpty(benchmarkVersion)`, and --benchmark cis-1.12 never enters that branch.
The warning is printed by getPlatformInfo(), which Go evaluates as an ARGUMENT
before the function runs, unconditionally, and whose kubectl probe fails
because this Job sets automountServiceAccountToken: false and has no API
credentials.

PROOF 2 — the falsifiable one. If the 1.18 fallback HAD determined the
benchmark, the loaded config would not be cis-1.12. Upstream's own mapping at
tag v0.15.6:
$ gh api repos/aquasecurity/kube-bench/contents/cfg/config.yaml?ref=v0.15.6 --jq .content | base64 -d | sed -n '/version_mapping/,/target_mapping/p'
  "1.18": "cis-1.6"
  ...
  "1.32": "cis-1.12"
  "1.33": "cis-1.12"
  "1.34": "cis-1.12"
(exit code: 0)

=> 1.18 maps to cis-1.6, NOT cis-1.12, and the run demonstrably loaded
cfg/cis-1.12/*. The two are mutually exclusive, so the run is conclusively
against cis-1.12 and the warning is cosmetic. Recorded because an earlier
working note in this project assumed 1.18 mapped to cis-1.5; it does not.

kube-bench reported, in section 4 above:
  [PASS] 4.2.5 Ensure that the --streaming-connection-idle-timeout argument is not set to 0 (Manual)

The configured value IS zero on all three nodes, which is exactly what the
check forbids. Why it passed anyway, from cfg/cis-1.12/node.yaml at tag
v0.15.6:
      - id: 4.2.5
        tests:
          test_items:
            - flag: --streaming-connection-idle-timeout
              path: '{.streamingConnectionIdleTimeout}'
              compare: {op: noteq, value: 0}
            - flag: --streaming-connection-idle-timeout
              path: '{.streamingConnectionIdleTimeout}'
              set: false
          bin_op: or

=> THE VALUE IS THE STRING "0s", A GO DURATION, AND THE COMPARISON IS AGAINST
THE INTEGER 0. "0s" != "0" is true, so the first test item passes and the
or-clause short-circuits to PASS. The control's intent — that idle exec /
attach / port-forward streams get reaped — is NOT met: 0s disables the timeout
entirely. Because --include-test-output prints observed values only for
NON-passing checks, this value never appears in sections 3 or 4, so a reader
cannot catch it from the transcript alone.

WHERE THE 0s CAME FROM IS UNVERIFIED — the one triage input in this phase with
no probe behind it. The working note behind this phase asserted the setting is
kind's doing and not kubeadm's, and that kubeadm's own default is 4h0m0s. NO
COMMAND WAS RUN FOR EITHER HALF, so neither is repeated here as fact and the
origin is NOT used to classify the setting. It would not change the finding if
it were true: this phase refuses "it is the installer's default" as a defence
for 4.1.1 / 4.1.9 and 1.1.12, and the same standard applies here. THE FINDING
STANDS ON ITS OWN — 0s is the live value on all three nodes above, so idle
exec / attach / port-forward streams are never reaped, and it is NOT
remediated.

And the METHODOLOGICAL POINT MUST NOT BE DROPPED EITHER: a kube-bench PASS is
not proof of compliance. At least one PASS in this run is an artifact of a
string-versus-integer comparison, and no systematic audit of the other 62 was
performed. Report the figure as "63 checks kube-bench scored as passing", never
as "63 controls verified compliant". That is this repo's own
claims-must-not-exceed-reality standard applied to the scanner itself.
