The intended before/after probe for seccompDefault was "an unconfined pod

[raw: t4-probe-readings.txt]

On kind the "node" is itself a Docker container carrying Docker's own default
seccomp profile, and every process inside it — kubelet, containerd and every
pod container — inherits that one filter. `Seccomp: 0` is not reachable on
this platform. An after-run showing `Seccomp: 2` would therefore have
"confirmed" seccompDefault while proving nothing whatsoever.

The replacement discriminator was established by control, on this cluster, in
the same session. The control is an existing nginx pod in `demo`, which
declares seccompProfile: RuntimeDefault explicitly; the subject is the probe
pod, which declares no seccompProfile at all:

  CONTROL  nginx-775678cbbd-mmrxb (seccompProfile: RuntimeDefault)
    crictl inspect ->           "seccomp": {}
      and an OCI spec block with "architectures" and a full syscall list
    /proc/1/status ->           Seccomp:	2
                                Seccomp_filters:	2

  SUBJECT  r3-seccomp-pids-probe (no seccompProfile field)
    crictl inspect ->           "seccomp": {
                                  "profile_type": 1
                                }
      and no OCI seccomp block at all
    /proc/1/status ->           Seccomp:	2

(exit code: 0)
[raw: t4-seccomp-control-vs-subject.txt]

=> THE DISCRIMINATOR IS Seccomp_filters, NOT Seccomp. One filter means nothing

a crictl seccomp block that is no longer `"profile_type": 1`. Asserting

1) THE PULL-GATE — WHETHER AlwaysPullImages COULD BE INCLUDED AT ALL
============================================================

AlwaysPullImages forces the kubelet to pull every image on every pod create,
so it converts "the image happens to be on the node" into "the registry must
serve the image, now". kind side-loads its own system images into the node
image; if any of them cannot actually be pulled from a registry, a cluster
built with AlwaysPullImages never gets CNI or DNS and the rebuild strands the
lab. So the plugin was gated on a real pull of each image, from a real node,
before the entry was written into the config.

METHOD, AND A NEGATIVE CONTROL FIRST. Every ref was pulled with
`docker exec seclab-worker crictl pull <ref>`. A success prints either a
download or "Image is up to date". That second form only counts as evidence if
crictl actually contacts the registry rather than short-circuiting on a local
hit, so a deliberately bogus tag was pulled first:
