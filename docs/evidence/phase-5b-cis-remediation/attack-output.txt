The honest summary is that 5b fixes the flags and kubelet fields that are one

The intended before/after probe for seccompDefault was "an unconfined pod

Seccomp:	2

(exit code: 0)
[raw: t4-probe-readings.txt]

On kind the "node" is itself a Docker container carrying Docker's own default
seccomp profile, and every process inside it — kubelet, containerd and every
pod container — inherits that one filter. `Seccomp: 0` is not reachable on
this platform. An after-run showing `Seccomp: 2` would therefore have
"confirmed" seccompDefault while proving nothing whatsoever.

The replacement discriminator was established by control, on this cluster, in
the same session. The control is an existing nginx pod in `demo`, which
declares seccompProfile: RuntimeDefault explicitly; the subject is the probe
pod, which declares no seccompProfile at all:

  CONTROL  nginx-775678cbbd-mmrxb (seccompProfile: RuntimeDefault)
    crictl inspect ->           "seccomp": {}
      and an OCI spec block with "architectures" and a full syscall list
    /proc/1/status ->           Seccomp:	2
                                Seccomp_filters:	2

  SUBJECT  r3-seccomp-pids-probe (no seccompProfile field)
    crictl inspect ->           "seccomp": {
                                  "profile_type": 1
                                }
      and no OCI seccomp block at all
    /proc/1/status ->           Seccomp:	2
                                Seccomp_filters:	1
(exit code: 0)
[raw: t4-seccomp-control-vs-subject.txt]

=> THE DISCRIMINATOR IS Seccomp_filters, NOT Seccomp. One filter means nothing
above the inherited Docker profile was applied; two means Kubernetes applied

an identical pod with NO seccompProfile field shows `Seccomp_filters:	2` and
a crictl seccomp block that is no longer `"profile_type": 1`. Asserting
`Seccomp: 2` proves nothing and must not be used.

1) THE PULL-GATE — WHETHER AlwaysPullImages COULD BE INCLUDED AT ALL
============================================================

AlwaysPullImages forces the kubelet to pull every image on every pod create,
so it converts "the image happens to be on the node" into "the registry must
serve the image, now". kind side-loads its own system images into the node
image; if any of them cannot actually be pulled from a registry, a cluster
built with AlwaysPullImages never gets CNI or DNS and the rebuild strands the
lab. So the plugin was gated on a real pull of each image, from a real node,
before the entry was written into the config.

METHOD, AND A NEGATIVE CONTROL FIRST. Every ref was pulled with
`docker exec seclab-worker crictl pull <ref>`. A success prints either a
download or "Image is up to date". That second form only counts as evidence if
crictl actually contacts the registry rather than short-circuiting on a local
hit, so a deliberately bogus tag was pulled first:

8b) THE ONE MISS: 4.2.13's GROUND-TRUTH PROBE READS THE WRONG CGROUP
------------------------------------------------------------

The check flipped WARN -> PASS, and correctly so: podPidsLimit: 4096 really is
in /var/lib/kubelet/config.yaml, which is what the check reads. But the
runbook's ground-truth probe — `cat /sys/fs/cgroup/pids.max` from inside the
container — still returns 18999, the same value section 2g recorded as
"unexplained". So the probe as designed cannot distinguish a working
podPidsLimit from a broken one. The mechanism was found rather than guessed.

FIRST, WHERE 18999 COMES FROM. It is systemd's default inside the kind node:

$ docker exec seclab-worker sh -c 'systemctl show --property=DefaultTasksMax'
DefaultTasksMax=18999
$ docker exec seclab-worker sh -c 'cat /proc/sys/kernel/threads-max'
threads-max=126663
(exit code: 0 — systemd's documented default is DefaultTasksMax=15%, and
126663 * 0.15 = 18999.45, truncating to 18999)

That closes the section 2g open question: 18999 is not a kubelet value, not a
Docker value and not kernel.pid_max. It is systemd's TasksMax default applied
to the container scope, and it survived a full cluster rebuild because it is a
property of the node image, not of the cluster.

SECOND, WHERE 4096 ACTUALLY IS. Every pids.max in the node's cgroup tree,
counted:
     22 18999      (container scopes — systemd's DefaultTasksMax)
      8 max        (unbounded parents, including the node root)
      7 4096       (the POD slices — one per pod on the node)
      1 126663     (kubelet-kubepods.slice)
(exit code: 0)

And pinned to this exact probe pod, by its own UID, so it is not a
coincidence-of-numbers argument:

  probe pod UID : 46f84866-c2cd-4aac-91c6-708a5115ee98
  4096   /sys/fs/cgroup/kubelet.slice/kubelet-kubepods.slice/kubelet-kubepods-besteffort.slice/kubelet-kubepods-besteffort-pod46f84866_c2cd_4aac_91c6_708a5115ee98.slice/pids.max
  18999  .../kubelet-kubepods-besteffort-pod46f84866_c2cd_4aac_91c6_708a5115ee98.slice/cri-containerd-76da7055c4d8...scope/pids.max
  18999  .../kubelet-kubepods-besteffort-pod46f84866_c2cd_4aac_91c6_708a5115ee98.slice/cri-containerd-2c5dc4247b19...scope/pids.max
(exit code: 0)
[raw: t41-pids-max-investigation.txt, t42-pids-max-pod-slice.txt]

=> THE KUBELET APPLIES podPidsLimit AT THE POD SLICE, ONE LEVEL ABOVE THE
CONTAINER. cgroup v2 enforces pids limits hierarchically, so 4096 is the
binding limit for the pod as a whole regardless of the 18999 each container
scope carries. The remediation IS in force; the probe was pointed one level too
low. THE CORRECT PROBE for 4.2.13 is the pod slice's pids.max on the node, not
`cat /sys/fs/cgroup/pids.max` from inside the container. The runbook's
"expect 4096" for the in-container reading is wrong and is corrected there.

This is worth stating plainly: had the drill accepted "4.2.13 flipped to PASS"
as sufficient, the broken probe would never have been found. The check passing
and the probe failing disagreed, and the disagreement was the finding.
