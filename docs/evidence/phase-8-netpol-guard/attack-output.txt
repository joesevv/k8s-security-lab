============================================================
0) THE THESIS — WHAT ADMISSION STRUCTURALLY CANNOT DO
============================================================

ADMISSION VALIDATES THE OBJECT BEING WRITTEN. That is its entire contract. It
receives an AdmissionReview for a specific resource on a specific verb and
answers allow/deny. It is excellent at "this Pod must not be privileged" and
it is the only layer that can make a bad state impossible rather than
temporary.

THE VIOLATION IN THIS PHASE IS CAUSED BY DELETING AN UNRELATED OBJECT.

  $ kubectl delete networkpolicy default-deny -n demo

At that instant no pod is created, no pod is updated, no pod is touched in any
way. The `signed-app` pod keeps running, unmodified, with the same spec and
the same uid — and it silently loses Ingress protection, because the only
policy that was selecting it for Ingress is gone. There is NO AdmissionReview
for that pod at the moment its protection disappears. A ValidatingPolicy has
nothing to evaluate. A PSA profile has nothing to evaluate. There is no
request. This is a structural limit of the request path, not a gap in this
lab's policy set — section 3d shows the five Kyverno policies matching only
`pods`/`deployments`/`jobs` on `CREATE, UPDATE`, never `networkpolicies`.

Only something that CONTINUOUSLY RECONCILES OBSERVED STATE can notice. That is
what phase 8 builds.

IT ALSO CLOSES A GAP PHASE 7 MEASURED. ArgoCD's `demo-workloads` Application
syncs `workloads/` and nothing else; `network/` is outside its scope. Phase 7
drifted an out-of-scope object and watched ArgoCD ignore it for 4 min 57 s
while reporting `Synced`. Section 3e re-confirms it here: throughout the
entire unprotected window, ArgoCD reported `Synced` / `Healthy`.

THE PHASE IS RUN TWICE, WITH ONE FLAG CHANGED.
  STAGE 1 (section 3): --remediate=false. The invariant breaks. The controller
  reports it on scan 4 and then reports it again on scans 5, 6, 7, 8, 9 and 10
  and does nothing about it. The pod stays reachable.
  STAGE 2 (section 4): --remediate=true. The SAME violation is restored in
  19 milliseconds, on the first scan.
The contrast between those numbers is the deliverable. Detection and
correction are different products, and the flag between them is one boolean.

IT IS NOT PREVENTION EITHER. Section 4d is the uncomfortable arithmetic: a
controller that reconciles on a timer leaves a real window in which the pod
genuinely was unprotected. This phase measured that window at the network
level, not in theory — 226 milliseconds after the delete, a host that had been
refused for 5 full seconds got HTTP 200 from the app.

1) GROUND TRUTH — THE POLICIES, THE PODS, THE ISOLATION MATH
============================================================

1a. The four NetworkPolicies in `demo`, reduced to the only two fields the
invariant depends on:

$ kubectl get networkpolicy -n demo -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}podSelector={.spec.podSelector}{"\t"}policyTypes={.spec.policyTypes}{"\n"}{end}'
allow-client-egress-to-nginx	podSelector={"matchLabels":{"access":"nginx"}}	policyTypes=["Egress"]
allow-dns	podSelector={}	policyTypes=["Egress"]
allow-nginx-ingress-from-client	podSelector={"matchLabels":{"app":"nginx"}}	policyTypes=["Ingress"]
default-deny	podSelector={}	policyTypes=["Ingress","Egress"]
(exit code: 0 — four policies, as committed in network/)

=> `allow-dns` has an EMPTY podSelector and `Egress`. That single fact is what
   makes this demo produce one specific violation instead of a general
   collapse: after `default-deny` goes, every pod in the namespace is STILL
   Egress-isolated, by `allow-dns`.

1b. The pods, with their labels:

$ kubectl get pods -n demo --show-labels

1c. The isolation math, worked from 1a and 1b. Kubernetes semantics: a pod is
isolated for a direction if ANY policy selects it with that direction in
policyTypes; an empty podSelector selects every pod.

  WITH all four policies:
    nginx pods      Ingress: default-deny{} + allow-nginx-ingress-from-client
                    Egress:  default-deny{} + allow-dns{}
    signed-app      Ingress: default-deny{}                    <-- SOLE source
                    Egress:  default-deny{} + allow-dns{}

  WITHOUT default-deny:
    nginx pods      Ingress: allow-nginx-ingress-from-client    still covered
                    Egress:  allow-dns{}                        still covered
    signed-app      Ingress: NOTHING                            <-- VIOLATION
                    Egress:  allow-dns{}                        still covered

=> Deleting `default-deny` does not break the namespace. It breaks exactly ONE
   pod in exactly ONE direction. `signed-app` carries `app=signed-app`; the
   only remaining Ingress policy selects `app=nginx`. Nothing else selects it.
   Sections 3 and 4 test this prediction rather than assuming it.

(Note on provenance: the compact listing in 1a was re-printed after this phase
restored the baseline, so its content is the end state as well as the start
state; the full pre-state `-o yaml` dump taken before anything was touched
carries the identical podSelector and policyTypes values for all four.)

1d. A consequence that dictates HOW the reachability probe had to be built.
Because `allow-dns` keeps EVERY pod in `demo` Egress-isolated with only
53/UDP+TCP to CoreDNS allowed, a phase-2c-style attacker pod INSIDE `demo`
could not have demonstrated this regression: its egress to `signed-app` stays
blocked before and after, so the probe would have failed identically in both
states and proved nothing. The probe therefore had to originate OUTSIDE the
reach of `demo`'s policies. Section 3a establishes one that works and, just as
importantly, one that does not.

3a. CALIBRATING THE PROBE — one source works, one does not. NetworkPolicy is
an API-level statement; whether the CNI enforces it is a separate question and
this phase answers it with real TCP. With all four policies in place:

$ docker exec seclab-worker curl -m 5 -s -o /dev/null -w "HTTP:%{http_code} time=%{time_total}\n" http://10.244.1.7:8080/

HTTP:200 time=0.005990
(exit code: 0)

=> `signed-app` runs on seclab-worker2 (10.244.1.7). From seclab-worker — a
   DIFFERENT node — it is unreachable. From seclab-worker2 — the pod's OWN
   node — it answers in 6 ms. kindnet does not police traffic from a pod's own
   node, which is expected (kubelet probes have to work). So:
     PROBE SOURCE   = seclab-worker, the remote node. Its source address is
                      not a pod in `demo`, so no `demo` egress policy applies
                      to it, and what it hits is purely `signed-app`'s INGRESS
                      isolation. This is the discriminator.
     LIVENESS CHECK = seclab-worker2, the local node. Its HTTP 200 proves the
                      app is up and serving, so a timeout from the remote node
                      is a policy decision and not a dead process.

   A phase-2c-style attacker POD inside `demo` was considered and rejected on
   the evidence of section 1d: `allow-dns` keeps every `demo` pod
   Egress-isolated with only DNS allowed, so that probe stays blocked in both
   states and cannot discriminate. This is a deviation from the phase-2c
   method, made because the phase-2c method cannot see this particular
   regression.

  THE CONTROLLER'S OWN NUMBER is the detection latency: 6.950 s at a 15-second

  shipped default of 30 s the bound is ~30 s. A single-replica controller that
  is restarting, throttled, or wedged has no bound at all.

  fires; it is not the exposure. Between the delete and the next scan the pod
  really was reachable — measured, at 226 ms, by a host that had been timed
  out moments earlier. Only admission control can make an exposure window
  zero, and admission control cannot see this event at all. That is the whole
  shape of phase 8: the layer that could make it zero cannot see it, and the
  layer that can see it cannot make it zero.

5b. WHAT IN-CLUSTER WOULD REQUIRE — three gates, none of which an agent may
open. This is a finding about the lab, not an excuse:

  1. A CI CHANGE. `.github/workflows/supply-chain.yml` builds exactly one
     context, `app/signed-app`, and pushes on `push: branches: [main]`. A
     second image needs a second build/push job.
  2. A MERGE TO `main`. The publish step is gated on that branch, so a feature
     branch cannot produce the image.
  3. A COSIGN SIGNATURE. `require-keyless-signed-ghcr` Denies any
     `ghcr.io/joesevv/k8s-security-lab/*` image in `demo` that lacks a
     Sigstore keyless signature from the pinned workflow identity. CI would
     have to sign this image exactly as it signs `signed-app`.

  AND `kind load` CANNOT ROUTE AROUND IT. Phase 5b enabled
  `--enable-admission-plugins=NodeRestriction,AlwaysPullImages`, which forces
  the kubelet to pull from a registry, so side-loading a locally-built image
  no longer works. That is the lab's own hardening closing the door — a real
  trade-off, worth recording rather than apologising for: AlwaysPullImages
  removes a genuine attack path (a node-local image masquerading as a trusted
  tag) and in exchange makes local iteration require a full publish pipeline.

  A FOURTH GATE, FOUND WHILE WRITING THE MANIFEST. A netpol-guard pod in
  `demo` could not reach the apiserver. Under `default-deny` every pod is
  Egress-isolated and the only carve-out is `allow-dns` (53/UDP+TCP to
  CoreDNS). The apiserver is Service `kubernetes.default`:

5c. IT RECONCILES ON A TIMER. Quantified in 4d from this phase's own
timestamps: 6.950 s to notice at `--interval=15s`; up to ~30 s at the shipped
default. During that window the pod is not protected — and 3c proves that is
not a theoretical statement.

5d. IT ONLY CHECKS THAT ISOLATION EXISTS, NOT THAT IT IS CORRECT. This is the
limit most likely to be over-read by a reader who wants good news. A policy
like this one:

  podSelector: {}
  policyTypes: [Ingress, Egress]
  ingress: [{}]        # allow from everywhere
  egress:  [{}]        # allow to everywhere

satisfies this invariant COMPLETELY. Every pod would be "isolated" in both
directions and every scan would print `verdict=HOLDS`, while the namespace
was wide open. netpol-guard checks COVERAGE. It does not read rules, it does
not evaluate reachability, and nothing in this phase should be read as saying
`demo` is correctly segmented — phase 2c makes that argument, and this phase
only keeps its foundation from silently vanishing.

5e. SCOPE. One namespace per process (`demo` by default). NetworkPolicies
versus Pods, and nothing else — not Services, not Ingress objects, not CNI
enforcement, not other namespaces. Pods in `Succeeded`/`Failed` are skipped
(no running container to protect); that filter is in the cluster-facing scan
path and is NOT covered by a unit test.

5f. LEAST-PRIVILEGE RBAC, AND THE CONTRAST NOBODY SHOULD MISS. The committed
Role grants `list` on pods and `get, list, create` on networkpolicies, in ONE
namespace, via a namespaced Role and RoleBinding. It grants no `update`, no
`patch`, no `delete`, nothing cluster-scoped, no secrets. So "it will never
modify or delete a policy it did not create" is enforced by the APISERVER, not
by the code's good intentions. `watch` is deliberately absent because the
controller polls and never opens a watch — granting it would be unused
privilege.

  For contrast, in this same cluster: phase 7 section 2c found the
  `argocd-application-controller` ClusterRole byte-identical to the built-in
  `cluster-admin`. The remediation surface here is ONE object name in ONE
  namespace with no delete verb; the remediation surface there is `*/*/*`.
  Both are "a controller that fixes drift". They are not remotely the same
  security proposition.

5g. WHAT THE UNIT TESTS DO NOT COVER. They cover the pure isolation model:
selector semantics including the empty selector, policyTypes defaulting,
per-direction verdicts, policy attribution by name, and the shape of the
baseline object. They do NOT cover: the client-go call path, the scan loop,
the ticker, signal handling, the terminal-pod filter, the remediation function
against a real or fake apiserver (no envtest, no fake clientset), error and
retry behaviour, or RBAC-denied responses. Everything cluster-facing was
verified by RUNNING it against the live cluster, which is what sections 3 and
4 are — not by a test.

5h. SINGLE REPLICA, NO LEADER ELECTION. The committed Deployment sets
`replicas: 1`. Two replicas would both scan and both attempt the create; the
loser gets `AlreadyExists`, which the code handles by logging and moving on,
so it is safe rather than correct. It has not been tested with two.
