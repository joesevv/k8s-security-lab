============================================================
0) WHAT GITOPS IS, WHAT IT IS NOT, AND THE TWO-STAGE STRUCTURE
============================================================

GITOPS IS NOT ADMISSION CONTROL. It does not sit in the request path. It
cannot refuse a write. Everything phase 7 demonstrates happens AFTER the
apiserver has already accepted a change and AFTER the kubelet has already
started the resulting pod. That ordering is the whole subject of this phase
and it is measured, not asserted, in sections 4 and 5.

THE PHASE IS DELIBERATELY RUN TWICE, WITH ONE FLAG CHANGED.
  STAGE 1 (section 4): syncPolicy.automated.selfHeal = FALSE. A real security
  regression is applied to the live nginx Deployment. ArgoCD NOTICES — the
  Application flips to OutOfSync and names the exact resource. And then it
  does nothing at all. The weakened pod keeps serving for 10 min 8 s of
  continuous observation.
  STAGE 2 (section 5): selfHeal = TRUE. The SAME regression is applied. It is
  reverted automatically within 1.29 s.
The contrast between those two numbers is the deliverable. "Detection" and
"prevention" are different products and the flag between them is one boolean.

EVEN IN STAGE 2 IT IS NOT PREVENTION. Section 5c is the uncomfortable part:
when the drift was re-applied with selfHeal ON, the Kubernetes ReplicaSet
controller still created a weakened pod, the kubelet still pulled its image,
and the container still STARTED — with a writable root filesystem — before
ArgoCD's revert killed it. A container ran without the control for roughly
one second. GitOps closes the window; it does not remove it.

THE REGRESSION CHOSEN IS ONE THE ADMISSION LAYER PERMITS. The drift removes
`readOnlyRootFilesystem: true` from the nginx container. PSA `restricted`
does NOT require that field, and none of this repo's 5 Kyverno policies check
it either. Section 4b proves the weakened pod was ADMITTED — every event is
Normal, there is no denial. So this is not a straw man: it is a genuine
weakening that phases 2b and 4 cannot see, which is precisely the gap a
GitOps controller is supposed to cover.

ARGOCD GRANTED ITSELF CLUSTER-ADMIN. Section 2c shows the application
controller's ClusterRole is byte-identical to the built-in `cluster-admin`.
The threat model's A2 "compromised GitOps controller" is no longer
hypothetical in this cluster; it is a ServiceAccount with `*/*/*`.

THE `argocd` NAMESPACE IS UNGATED. It carries no Pod Security labels at all,
and all 5 Kyverno policies select only `demo` and `demo-kyverno-only`. That
is three unenforced namespaces in this lab now: `cis-benchmark`, `falco`,
`argocd`. Section 7 states it with the evidence.

NOTHING HERE VERIFIES THE GIT CONTENT. Commit signature verification is NOT
configured (section 7). ArgoCD applies whatever is on `main`, faithfully. A
malicious commit to `main` would be synced with exactly the same diligence as
a good one — and with selfHeal ON it would be re-applied every time an
operator tried to remove it by hand.

NO CREDENTIAL WAS RETRIEVED IN THIS PHASE. `argocd-initial-admin-secret` was
created by the install and never read, decoded or used. The UI was never
logged into. Every observation below comes from `kubectl` against the
Application CR and the live objects.

7) LIMITS
============================================================

7a. IT REVERTS; IT DOES NOT PREVENT. Quantified in 5c: with selfHeal ON, a
weakened container was still created, started and run for ~1 s before being
killed. With selfHeal OFF it ran for 10 min 8 s. Neither number is zero. The
only layer in this lab that can make it zero is admission control, and
admission control does not check this field (4b).

7b. IT ONLY SEES `workloads/`. Demonstrated for 4 min 57 s in section 6.
Everything else in `demo` — the RBAC, the 4 NetworkPolicies, the SealedSecret
— is unmanaged and unprotected. This is a deliberate scoping choice, not an
oversight, but the consequence is real and is now measured rather than
assumed.

7c. ARGOCD IS CLUSTER-ADMIN AND SITS IN AN UNGATED NAMESPACE. Section 2c
proves the application controller's ClusterRole is byte-identical to
`cluster-admin`; section 2d proves the `argocd` namespace has no PSA label
and is outside all 5 Kyverno policies. THREE UNENFORCED NAMESPACES NOW:
`cis-benchmark`, `falco`, `argocd`. The lab's controls are concentrated in
`demo`, and each new operational component has been installed outside them.
